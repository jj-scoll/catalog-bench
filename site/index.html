Lakehouse catalogs under concurrent writes

A lakehouse catalog is the service that records which data files make up a table, so every write ends with a commit to it. This open benchmark measures what happens when several writers commit at once, with two workloads: a commit-rate ramp that finds how many tiny commits per second each catalog accepts as writers are added, and a pipeline workload that pushes a batch load through each option and checks every row afterwards. Every number on this page is rebuilt from the result files in the repository.

How to read this

  • Compare within one table. Each environment and each run shape has its own table, because numbers from different machines or different loads do not line up.
  • Check how many runs are behind a number. The commit-rate ramp shows the median of its repetitions with the lowest and highest beside it. Every pipeline row is a single run, so treat small differences there as noise.
  • Times are in milliseconds (ms) below one second and in seconds (s) above. A median is the middle value; p95 is the value 95 in 100 were faster than.
  • Problems are written out. A run that fell behind, lost a batch or did not verify says so in words, not only in colour.

    What each entry measures

    Workload 2

    Pipeline workload

    A load arrives as traces, and each trace is split into batches of rows. Workers write the batches, one at a time each. When all of a trace's batches are in, a finaliser closes the trace, and a reader then loads the whole trace back. Some batches are delivered twice on purpose, and a write that fails is delivered again. Afterwards one trace is reprocessed under a new version that must replace the old rows, and every trace is read back and compared row by row with what was acknowledged.

    Each row is a single run. Nothing here was repeated, so there is no spread to judge noise by. Read a large gap as a finding and a small one as nothing.

    Batch data did not go to the same place in every row. Rows backed by S3, Aurora or Amazon S3 Tables wrote batch data to S3. Rows backed by something on the runner (local Postgres, the Iceberg SQL catalog, Lakekeeper, Polaris) wrote it to the runner's local NVMe disk, so their batch writes of a few milliseconds are disk writes and are not comparable with the S3 rows. Aurora was one provisioned db.r8g.xlarge instance and one Serverless v2 cluster set to 0.5 to 16 ACU, both PostgreSQL 16.8.

    What the columns mean

    Kept up
    For a paced run, batches are scheduled at a fixed rate. The run kept up if no batch started more than one second after its scheduled time. The rate achieved counts every acknowledged write, including the deliberate repeat deliveries, over the whole load including closing the traces, so it can sit a little above or below the rate asked for. An unpaced run has no schedule: its rate is simply how fast the option went.
    Batch write
    Time for one batch to be durable and acknowledged: the median, then p95. Options that commit once per trace only write files here; their commit cost shows up under "Close a trace".
    Close a trace
    The slowest finalise call in the run, including replacing an older version of the trace. Retries are the finaliser's own, after a conflict with a concurrent write.
    Read one trace
    Median time for a reader to load every current row of one trace. Where the option runs maintenance (compaction), the time after it is shown too.
    Failed writes
    Write attempts that raised an error. Each is delivered again, up to three deliveries in all. A batch that never got written is called out.
    Verified
    No rows missing, duplicated or left over from an old version, and the reprocessed trace verified as well.

    What each option does

    Method

    Commit-rate ramp

    N writer processes each open their own connection and commit one single-row insert at a time, as fast as the system acknowledges them, for a fixed period. A commit counts only when the client was told it succeeded.

    A run is marked verified when the rows found afterwards equal the acknowledged commits, allowing for failed commits that landed anyway.

    Single-row commits are the worst case for a catalog on purpose: they isolate commit cost from data volume.

    Results from a workstation or a shared CI runner are noisy. Compare systems within one run on one machine, not across machines. That is why each environment here has its own ranking, and why runs shorter than 30 seconds or with a single repetition are labelled as not comparable.

    The Python client's cost is negligible for raw Postgres (checked against pgbench). For the Iceberg systems the Python client (pyiceberg) and its object writes are most of each commit, so those rows measure the client as much as the catalog.

    Pipeline workload

    Worker processes take batches from a queue and write one at a time. Paced runs schedule batches at a fixed rate whether or not earlier ones have finished, so a slow option falls behind instead of slowing the load down. Unpaced runs hand every batch over at once.

    Delivery is at least once: a failed write is delivered again, up to three times in all, and some batches are delivered twice even though the first delivery succeeded. An option has to cope with both without leaving duplicate rows.

    The same option can run against different backings, and the load comes in several shapes. Each table above holds one shape, so its rows faced the same load.

    Add your catalog

    Copy bench/systems/postgres.py to a new file in the same directory and edit it. Any module there with a System class is registered automatically. If the system needs a service, add it to compose.yaml.

    • Use default settings. If you tune something, make it a separate entry whose name and docstring say what changed.
    • commit_one must not return until the commit is durable by the system's own definition, and must raise if it failed. No client-side batching or retries beyond what the client library does by default.
    • State what the client is. For systems where the client does real work per commit, the client is part of the result.

    The results format is the contract: a driver written in any language can produce it for the same workload. The full interface is in docs/adding-a-system.md in the repository. Open the repository on GitHub
